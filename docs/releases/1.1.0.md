## Attach to a running Main

- `dchat acp` is an attach-only ACP v1 stdio frontend for an already-running
  terminal Main. It shares Main's public history, input and job notices through
  private Unix IPC, without starting another runtime or opening another database.
  Disconnect only detaches; Stop Main cancels Main/queued inputs, not its jobs.
- `dchat acp list` discovers this user's running Mains and their endpoints,
  session IDs, cwd, title and model. `dchat acp --endpoint <socket>` attaches to
  one without choosing a store/config; endpoints outside the private directory
  are refused. `DCHAT_IPC_DIR` explicitly relocates that directory for both sides.
- Standard prompts work without private retry metadata. Generic clients receive
  committed public messages once, not duplicate live drafts. Disposable previews
  require the documented shared-Main v1 capability and cleanup handling. Optional
  retry keys retain bounded deduplication; repeated JSON-RPC IDs alone do not
  provide exactly-once admission. Attach still refuses new sessions and forwarded MCP.

## A separate ACP host for Zed New Thread

`dchat acp serve` runs an opt-in foreground stdio host. Unlike attachment, it can
create ACP-owned sessions without a terminal owner, then list, load, prompt,
cancel and close them. Each has an unpredictable stable ID, canonical cwd and
separate SQLite store; it never aliases the configured terminal database.
Load requires the original cwd and matching forwarded MCP configuration and
replays committed public history before replying, excluding reasoning/system
entries and live drafts. Jobs and native tools use the session cwd without
changing the host process cwd.

Configure a Zed custom external agent (use an absolute command path if needed):

```json
{
  "agent_servers": {
    "durable-chat": {
      "type": "custom",
      "command": "dchat",
      "args": ["acp", "serve"],
      "env": {}
    }
  }
}
```

Select **durable-chat** in Agent Panel → **New Thread**. Import Threads uses
list/load, not new-session creation. For an empty-MCP profile, remove configured
and extension-provided context servers; optionally add `--no-mcp` to reject any
forwarded servers explicitly.

- One host per private registry, guarded by a permanent SQLite-exclusive mutex;
  at most **16 simultaneously open sessions**. Close a session runtime to free
  a slot, or choose another `--sessions-dir` for an independent host. Requires
  local filesystem SQLite locking. Never remove/replace a live
  `registry-lock.sqlite`. Pre-fix development `registry.lock` markers fail closed:
  stop all old hosts before removing those markers offline; do not mix host versions.
- EOF/SIGINT/SIGTERM checkpoint and close runtimes, MCP children and locks.
  Closing retains history/jobs; paused jobs resume on load. Session cancellation
  addresses only that session's Main. There is no background host daemon.
- Serve accepts **only explicit session-forwarded stdio MCP**, with literal
  arguments/environment and separate children per session; no global/project MCP
  discovery. HTTP/SSE and invalid configurations fail explicitly. Trusted children
  inherit the host environment. State/cwd isolation is **not a security sandbox**:
  tools retain launching-user authority, not editor-managed permissions/auth.
- JSON-RPC-only stdout; unexpected internal errors are redacted on stderr/wire.
  Deliberately read public agent/tool data is not a secret-filtered channel.
- Text/resource-link prompts and committed-message output only, not token-draft
  streaming. No editor file/terminal permission bridge, model picker, additional
  workspace roots, custom system prompts, images/audio/embedded resources or
  session deletion/resume. See the [README](../../README.md#acp-host-for-zed-new-thread-110)
  for protocol bounds and setup. No Zed GUI trial or universal ACP conformance claim.

## OpenAI/Codex model discovery, including Sol and Astra

The GPT-6.2 work adds coverage for `gpt-6.2-sol` and `gpt-6.2-astra` on OpenAI and
Codex, named-provider identities, Responses tools and effort serialization. The
subsequent catalog change replaces the temporary static compatibility definitions
with Pi's bundled plus native remote catalog; a snapshot remains a test fixture,
not runtime model registration. Pi dependencies are aligned to **1.5.2** by #17.

Startup performs a bounded 10-second canonical-provider refresh before exact
configured-ID validation and named-alias registration. Pi's native four-hour
freshness avoids repeated downloads within a process; catalog state is in memory
and restart refreshes again. `PI_OFFLINE` disables network refresh; refresh failure
or timeout reports a diagnostic and retains Pi's bundled/previous catalog. The
picker does not download catalogs or refresh OAuth. Missing IDs fail without
fallback. No fabricated model ID or application allowlist is introduced.

Catalog loading uses empty in-memory factory credentials with personal Pi profile
loading disabled; actual refresh/generation retains durable-chat's existing
`PiAuthStore`. Discovery does not grant model access or validate account entitlement.
Default runtime thinking off omits an effort override; explicit effort handling
uses Pi's model metadata. Existing **named OpenAI OAuth transport limitations are
pre-existing and unchanged**: use the built-in OpenAI name for OpenAI OAuth or the
dedicated Codex transport. See [model discovery policy](../openai-models.md).

## Compatibility and validation scope

Node.js **22.19.0 or newer** is required; both `dchat` and `durable-chat` aliases
remain available. Existing native auth/store locks and attach mode remain separate
from serve. No Substrate service deployment, global installation or source-launcher
change is part of this release. Closed/unmerged authentication PR #1 is excluded.

Offline/synthetic checks do not establish real provider acceptance, live account
access, editor GUI behavior or production MCP operation. No live provider/auth,
personal store, clipboard or real MCP validation is claimed.
